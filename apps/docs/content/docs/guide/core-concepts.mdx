## Core Concepts

### CosmosQL Architecture Overview

CosmosQL is built with a layered architecture designed for type safety, performance, and developer experience:

**1. Client Layer**

- **`CosmosClient`**: Core HTTP client with authentication, retry logic, and connection pooling
- **`ContainerClient<TSchema, TPartitionKey>`**: Type-safe container operations
- **`CosmosAuth`**: Handles Azure CosmosDB authentication tokens (HMAC-SHA256 signatures)

**2. Schema System**

- **`ContainerSchema`**: Defines container structure and partition keys
- **`FieldBuilder`**: Fluent API for defining field types and constraints
- **Runtime vs Type-level**: Dual representation for validation (type-level) and inference

**3. Operations Layer**

- **`FindOperations`**: Query and retrieval operations (findUnique, findMany, query)
- **`CreateOperations`**: Document creation with bulk support (create, createMany)
- **`UpdateOperations`**: Document updates and upserts (update, upsert)
- **`DeleteOperations`**: Document deletion

**4. Type System**

- **Field-level type inference**: Preserves literal types from schema definitions
- **Operation type safety**: Create/Update/Find operations are fully typed
- **Advanced type utilities**: Required/optional field detection, select result typing

**Key Design Principles:**

- **Zero Runtime Overhead**: All validation happens at compile time
- **Direct REST API**: No SDK abstraction layers, just HTTP requests
- **Partition Key Enforcement**: Type-level guarantees prevent expensive queries
- **TypeScript-First**: Built for TypeScript from the ground up

### Understanding CosmosDB Fundamentals

Before diving into CosmosQL, it's crucial to understand how CosmosDB works. CosmosDB is fundamentally different from traditional SQL databases, and these differences shape how CosmosQL works.

<Callout type="info" title="Important">

CosmosDB is a distributed, globally scalable database. Understanding its core concepts—especially partition keys and Request Units—is essential for writing efficient, cost-effective queries with CosmosQL.

</Callout>

#### Partition Keys

CosmosDB achieves its performance by sharding data across multiple physical partitions. The **partition key** is a property of your document that determines which partition stores it. This design choice has major performance and cost implications:

**Within-Partition Queries**

When you query data within a single partition (by providing the partition key), CosmosDB can quickly locate and retrieve the data. These queries are:

- **Fast**: Typically 1-5 Request Units
- **Cost-effective**: Minimal resource consumption
- **Scalable**: Performance stays consistent as data grows

**Cross-Partition Queries**

When you query across partitions (without specifying a partition key), CosmosDB must scan every partition in your container. These queries are:

- **Expensive**: Typically 50-100+ Request Units (10-100x more expensive)
- **Slow**: Must scan all partitions sequentially
- **Costly at scale**: Costs grow dramatically as your data grows

**Transactions**

CosmosDB supports transactions, but **all documents in a transaction must share the same partition key**. This is a hard limitation of distributed systems—you can't atomically modify data across partitions.

**Partition Key Selection**

Choosing the right partition key is critical. Good partition keys have:

- **High cardinality**: Many unique values
- **Even distribution**: Data spread evenly across partitions
- **Query alignment**: Matches your most common query patterns

Poor choices lead to "hot partitions" (uneven load) and high costs.

<Callout type="warning" title="Why CosmosQL Enforces Partition Keys">

Because partition keys are so critical, CosmosQL requires them at the type level. You **cannot** accidentally write a cross-partition query without explicitly opting in, preventing costly mistakes before they reach production.

</Callout>

#### Request Units (RU)

CosmosDB uses **Request Units (RUs)** to measure and charge for operations. Understanding RUs helps you optimize costs:

| Operation | Typical Cost | Notes |
|-----------|-------------|-------|
| **Point Read** | ~1 RU | Reading a 1KB document by ID and partition key |
| **Query** | Varies | Based on complexity, document size, and partition scope |
| **Write Operations** | ~5-10 RU | Creating, updating, or deleting documents |
| **Cross-Partition Queries** | 10-100x more | Can cost 10-100x more than partition-scoped queries |

<Callout type="error" title="The Cost of Mistakes">

The cost difference between partition-scoped and cross-partition queries is dramatic. A simple mistake like forgetting a partition key can turn a **1 RU query into a 100 RU query**, increasing costs by 100x.

For applications processing thousands of requests per second, this difference can mean **hundreds or thousands of dollars** in additional costs per month.

</Callout>

**How CosmosQL Prevents This**

CosmosQL is designed to prevent these mistakes at compile time. By requiring partition keys in the type system, you're forced to think about query efficiency before your code runs, catching expensive mistakes during development rather than in production.

### Schema Definition

Schemas in CosmosQL are simple TypeScript objects that define your data structure:

```typescript
import { container, field } from 'cosmosql';

const posts = container('posts', {
  // Required fields
  id: field.string(),
  userId: field.string(),
  title: field.string(),
  content: field.string(),
  
  // Optional fields
  subtitle: field.string().optional(),
  publishedAt: field.date().optional(),
  
  // Fields with defaults
  viewCount: field.number().default(0),
  isPublished: field.boolean().default(false),
  
  // Arrays
  tags: field.array(field.string()),
  
  // Nested objects
  metadata: field.object({
    source: field.string(),
    version: field.number()
  }).optional(),
  
  // Special CosmosDB field
  ttl: field.number().optional() // Auto-delete after N seconds
}).partitionKey('userId'); // Define partition key

// Extract TypeScript type
type Post = typeof posts.infer;
// Result:
// {
//   id: string;
//   userId: string;
//   title: string;
//   content: string;
//   subtitle?: string;
//   publishedAt?: Date;
//   viewCount: number;
//   isPublished: boolean;
//   tags: string[];
//   metadata?: { source: string; version: number };
//   ttl?: number;
// }
```

**Why This Syntax?**

This approach combines the best of both worlds:

- **Drizzle-style**: Schemas are plain data structures, not decorators or classes. This makes them easy to compose, extend, and test.

- **Prisma-style**: The API feels familiar if you've used Prisma. The method names and patterns are intentionally similar to reduce cognitive load when learning.

- **Type inference**: Full TypeScript support with zero boilerplate. TypeScript automatically infers types from your schema—you don't need to manually define interfaces.

- **Composable**: Schemas can be reused and extended. You can define base schemas and extend them for different use cases.

- **No Runtime Overhead**: These schemas exist only in TypeScript. They're not validated at runtime—all checks happen at compile time. This means zero performance impact in production.

**Understanding Field Types:**

Each field type in CosmosQL maps to a JavaScript/TypeScript type:

- `field.string()` → `string`
- `field.number()` → `number`
- `field.boolean()` → `boolean`
- `field.date()` → `Date`
- `field.array(type)` → `Array<type>`
- `field.object(schema)` → Nested object type

The `.optional()` modifier makes fields nullable in TypeScript, while `.default(value)` provides a default value when creating documents. These modifiers only affect TypeScript types and default values—CosmosDB itself is schemaless, so the actual data can vary.

### Client Setup

The client is your main interface to CosmosDB. It manages connections, handles authentication, and provides typed access to your containers.

```typescript
import { createClient } from 'cosmosql';

// Create the client with connection details
const db = createClient({
  // Option 1: Connection string (recommended)
  // Get this from Azure Portal → CosmosDB Account → Keys
  connectionString: process.env.COSMOS_CONNECTION_STRING!,
  
  // Option 2: Separate endpoint and key (alternative)
  // endpoint: 'https://mydb.documents.azure.com:443/',
  // key: 'your-master-key',
  
  // Required: Database name
  // This must match a database in your CosmosDB account
  database: 'production'
}).withContainers({
  // Register your container schemas
  users,
  posts,
  comments
  // Add more containers as needed
});

// After registration, you get type-safe access to each container
db.users     // ContainerClient<User> - fully typed!
db.posts     // ContainerClient<Post> - fully typed!
db.comments  // ContainerClient<Comment> - fully typed!
```

**Connection String vs. Endpoint/Key:**

Both connection methods work identically. The connection string is more convenient (one value to manage), while endpoint/key gives you more control (useful if you need to construct the connection dynamically).

**Database Names:**

The `database` parameter must match an existing database in your CosmosDB account. CosmosQL doesn't create databases—you create them through the Azure Portal or Azure CLI. This keeps CosmosQL focused on query operations rather than infrastructure management.

**Container Registration:**

The `withContainers` call registers your schemas with the client. This is where TypeScript learns about your data structures. After registration, `db.users`, `db.posts`, etc. are fully typed with autocomplete and type checking.

**Connection Management:**

CosmosQL uses HTTP/2 connection pooling internally with:
- Maximum 50 concurrent sockets
- 10 free sockets maintained for reuse
- Automatic connection reuse for better performance
- You don't need to manage connection lifecycle manually
- The client handles reconnection and error recovery automatically

**Authentication:**

CosmosQL supports two authentication methods:

1. **Master Key Authentication** (recommended for development): Uses Azure CosmosDB shared secrets
2. **Connection String** (recommended for production): Encapsulates endpoint and key

Both methods use HMAC-SHA256 based signatures to authenticate each request. Tokens are generated automatically and include request method, resource path, and timestamp.

**Multiple Databases:**

If you need to work with multiple databases, create separate clients:

```typescript
const productionDb = createClient({
  connectionString: process.env.COSMOS_CONNECTION_STRING!,
  database: 'production'
}).withContainers({ users, posts });

const analyticsDb = createClient({
  connectionString: process.env.COSMOS_CONNECTION_STRING!,
  database: 'analytics'
}).withContainers({ events, metrics });
```
