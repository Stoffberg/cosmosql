## FAQ

Here are answers to the most commonly asked questions about CosmosQL. If you don't find what you're looking for, feel free to reach out through GitHub issues or the community Discord.

### Feature Support

#### Does CosmosQL support all CosmosDB features?

CosmosQL focuses on the core CRUD operations and query patterns that cover 95% of application use cases. This includes:

- Create, read, update, and delete operations
- Partition-scoped and cross-partition queries
- Point reads (by ID and partition key)
- Field selection, filtering, sorting, and pagination
- Bulk operations within partitions
- TTL (Time-To-Live) support
- Raw SQL queries for advanced use cases

**Advanced features** that are not yet supported but planned for future releases include:

- Stored procedures
- Triggers
- Change feed processors
- Graph API integration
- Multi-region write support
- Transactional batch operations across partitions

<Callout type="info" title="Using Advanced Features">

If you need these features now, you can use the official Azure SDK alongside CosmosQL for specific operations.

</Callout>

#### Does CosmosQL support MongoDB API or Gremlin API?

<Callout type="warning" title="SQL API Only">

No. CosmosQL is designed specifically for the SQL API (also called the Core API). The MongoDB API and Gremlin API have fundamentally different query patterns, data models, and semantics.

</Callout>

If you're using the MongoDB API, you might want to use a MongoDB-compatible library instead. For graph operations with the Gremlin API, you'll need the official Azure SDK or a Gremlin-compatible client.

### Language and Runtime

#### Can I use CosmosQL with JavaScript?

<Callout type="error" title="TypeScript Required">

No. CosmosQL requires TypeScript. The entire value proposition is built around compile-time type safety—catching errors before code runs, providing autocomplete, and preventing costly mistakes.

</Callout>

If you're using JavaScript, you have a few options:

1. Migrate to TypeScript (recommended for the type safety benefits)
2. Use the official Azure CosmosDB SDK, which has JavaScript support
3. Use a lighter-weight REST API client with manual type assertions

#### What Node.js version do I need?

CosmosQL requires **Node.js 18 or higher**. This ensures access to modern JavaScript features and built-in APIs that CosmosQL uses. If you're using an older version, you'll need to upgrade.

#### Does CosmosQL work in serverless environments?

<Callout type="info" title="Serverless Ready">

Yes! CosmosQL is designed to work well in serverless environments like AWS Lambda, Azure Functions, and Vercel Edge Functions. The minimal dependencies and zero runtime overhead make it ideal for cold starts and edge computing scenarios.

</Callout>

### Performance

#### What's the performance overhead compared to direct REST API calls?

CosmosQL has minimal performance overhead. Here's why:

- **No runtime validation**: All schema validation happens at compile time
- **Direct REST API calls**: CosmosQL generates HTTP requests that are identical to what you'd write manually
- **No SDK bloat**: Zero dependencies beyond Node.js built-ins
- **No connection pooling overhead**: Uses efficient connection management

<Callout type="info" title="Benchmark Results">

In benchmarks, CosmosQL operations are within **1-2% of manually written REST API calls**. The difference is negligible in real-world applications. The type safety benefits far outweigh this tiny overhead.

</Callout>

#### How does CosmosQL compare to the official Azure SDK in terms of performance?

CosmosQL is typically faster than the official SDK for most operations because:

- The SDK includes connection pooling, retry logic, and other features that add overhead
- CosmosQL is a thin wrapper that generates direct REST calls
- The SDK validates and transforms data at runtime, while CosmosQL does everything at compile time

<Callout type="warning" title="Trade-offs">

However, the official SDK has some optimizations for bulk operations and connection reuse that CosmosQL doesn't have yet. For most applications, the difference is small enough that developer experience and type safety matter more.

</Callout>

### Migration and Compatibility

**Q: Can I migrate an existing CosmosDB database to CosmosQL?**

A: Yes! CosmosQL works with existing databases without any migration. Here's what you need to do:

1. Define a schema that matches your current document structure
2. Create a client pointing to your existing database
3. Start using CosmosQL for new operations

There's no need to:
- Migrate existing data
- Change your database structure
- Update existing documents

CosmosDB is schemaless, so your existing documents continue to work. You can adopt CosmosQL incrementally—use it for new features while keeping existing code unchanged.

**Q: How do I handle schema changes in CosmosDB?**

A: CosmosDB is schemaless, which means you can add new fields to documents at any time without any migration. However, you should consider:

**Adding Fields:** Simply update your CosmosQL schema and add the new field. Existing documents without that field will have it as `undefined` in TypeScript (or use `.optional()` if it's truly optional).

**Removing Fields:** You can't truly "remove" fields from existing documents in CosmosDB. Consider:
- Using version numbers in documents and handling multiple versions in your code
- Writing migration scripts to update old documents
- Treating removed fields as optional in your schema

**Changing Field Types:** This can be tricky. You might need to:
- Version your documents and handle both formats
- Write a migration script to transform data
- Use a wrapper type that handles both old and new formats

The [Migration Guide](/docs/migration) has more detailed strategies for handling schema evolution.

**Q: Can I use CosmosQL alongside the official Azure SDK?**

A: Yes! CosmosQL and the Azure SDK can coexist in the same project. They use the same underlying database and don't interfere with each other. This is useful if you need:

- Advanced features from the SDK (like change feed) alongside CosmosQL's type safety
- Gradual migration from SDK to CosmosQL
- Specific SDK features for edge cases while using CosmosQL for common operations

Both libraries will work with the same containers and data.

### Production Readiness

**Q: Can I use this in production?**

A: Absolutely. CosmosQL is production-ready and designed for production use:

- **Stable API**: The core API is well-tested and stable
- **Minimal dependencies**: Fewer dependencies mean fewer breaking changes and security vulnerabilities
- **Type safety**: Catches bugs before they reach production
- **Performance**: Zero runtime overhead means production performance is excellent
- **Active maintenance**: The library is actively maintained with regular updates

Many teams are using CosmosQL in production environments handling real traffic and data. However, as with any database library, you should:

- Test thoroughly in staging environments
- Monitor your CosmosDB metrics (RUs, latency, errors)
- Have a backup plan (like falling back to the SDK) for critical operations
- Keep CosmosQL updated to the latest version

**Q: What's the error handling story?**

A: CosmosQL throws standard JavaScript errors that you can catch and handle. The library includes:

- `CosmosError` class for CosmosDB-specific errors (429 rate limits, 409 conflicts, etc.)
- Proper error codes matching CosmosDB status codes
- Type-safe error handling helpers

See the [Advanced Patterns](/docs/advanced-patterns) guide for detailed error handling examples.

- **Documentation**: Comprehensive guides covering all features

### Comparison to Alternatives

#### How does CosmosQL compare to the Azure CosmosDB SDK?

**CosmosQL Advantages:**

- ✅ **Zero dependencies** - No SDK bloat (50+ packages → zero dependencies)
- ✅ **Better type safety** - Compile-time guarantees vs runtime errors
- ✅ **Smaller bundle** - Perfect for serverless and edge computing
- ✅ **Better DX** - Type-safe API with autocomplete vs dynamic JavaScript
- ✅ **Performance** - Direct REST calls vs SDK abstraction layers
- ✅ **Partition key enforcement** - Type system prevents expensive queries

**Azure SDK Advantages:**

- ✅ **More features** - Change feed, stored procedures, database management
- ✅ **Mature ecosystem** - Better community support and documentation
- ✅ **Advanced capabilities** - Geospatial queries, transactions, etc.

**When to Choose:**

- Choose **CosmosQL** for new TypeScript projects prioritizing type safety and minimal dependencies
- Choose **Azure SDK** when you need advanced features like change feed or are heavily invested in the Azure ecosystem

#### How does CosmosQL compare to Prisma?

**Similarities:**

- Both provide type-safe query builders
- Both emphasize developer experience
- Both support TypeScript from the ground up

**Differences:**

- **Database support**: Prisma supports many databases (PostgreSQL, MySQL, SQLite, etc.), CosmosQL is CosmosDB-specific
- **Focus**: CosmosQL is optimized for CosmosDB patterns (partition keys, RU optimization)
- **Dependencies**: CosmosQL has zero dependencies, Prisma includes runtime dependencies
- **Query API**: CosmosQL uses CosmosDB SQL, Prisma uses its own query language

**When to Choose:**

- Choose **CosmosQL** for CosmosDB-specific applications needing partition key safety
- Choose **Prisma** for multi-database applications or when using traditional SQL databases

#### How does CosmosQL compare to Mongoose?

**CosmosQL Advantages:**

- ✅ **TypeScript native** - Built for TypeScript from ground up
- ✅ **No schema drift** - Strict schema enforcement at compile time
- ✅ **Modern API** - Async/await vs callback patterns
- ✅ **Type safety** - Compile-time validation vs runtime validation
- ✅ **Zero dependencies** - Minimal footprint

**Mongoose Advantages:**

- ✅ **Mature ecosystem** - Large community and extensive documentation
- ✅ **JavaScript support** - Works with JavaScript (no TypeScript required)
- ✅ **Rich middleware** - Hooks, validators, plugins

**Note:** Mongoose is designed for MongoDB, while CosmosQL is for Azure CosmosDB SQL API. They serve different databases.
